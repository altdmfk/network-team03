# 아키텍처 설계 및 문제 해결 기록

대규모 로그 스파이크 제어와 무손실 로그 파이프라인 구축 과정에서 직면한 기술 과제, 아키텍처 설계 결정 및 실측 검증 결과를 기록한 문서입니다.

---

## 1. 백오프 대기 중 메시지 유실 방지와 명시적 오프셋 커밋

- **문제**
  - 하위 SIEM(Graylog) 장애(HTTP 503 또는 타임아웃) 시 컨슈머가 지수 백오프 루프를 돌면서 세션을 유지하기 위해 `consumer.poll(0)`을 호출했습니다.
  - 일반적인 `poll(0)`은 브로커에서 새로운 메시지를 디큐하여 반환합니다. 반환된 메시지를 처리하지 않은 채 버리면, 장애 복구 후 오프셋 커밋 시 해당 메시지까지 함께 커밋되어 조용한 로그 유실이 발생하는 결함이 있었습니다.
  - 인자 없는 `commit(asynchronous=False)`를 호출하면 컨슈머가 폴링했던 모든 메시지의 오프셋이 일괄 커밋되는 문제도 있었습니다.
- **해결 방안**
  - 백오프 대기 루프 내에서 불필요한 `poll(0)` 호출을 제거했습니다.
  - 파티션 일시 정지(`pause`) 상태에서만 폴링하여 메시지 디큐 없이 하트비트를 유지하도록 변경했습니다.
  - Graylog 전달이 확인된 배치 내의 파티션별 최대 오프셋(`max_offset + 1`)만 명시적으로 커밋하는 `ExplicitOffsetCommitter`를 구현했습니다.
- **결과**
  - 장시간 백오프 대기 상황에서도 메시지가 유실되지 않음을 보장했습니다. 백오프 중 디큐 횟수 0회와 파티션별 정확한 오프셋 커밋을 단위 테스트로 검증했습니다.

## 2. 로그 단위 토큰 버킷 스로틀링 및 마이크로 배칭 구현

- **문제**
  - 초기 레이트 리미터는 배치 내 로그 개수와 무관하게 배치당 토큰 1개를 소모했습니다. 이로 인해 10건짜리 부분 배치와 100건짜리 전체 배치가 동일한 대기 시간을 소모하여 드레인이 지연되었습니다.
  - 순간적인 네트워크 지터 발생 시 배치가 충분히 채워지지 않은 채 소규모 HTTP 요청이 빈번하게 전송되는 비효율이 있었습니다.
- **해결 방안**
  - 전송할 실제 로그 개수(`acquire(len(messages))`)만큼 토큰을 소모하는 `TokenBucketRateLimiter`를 구현했습니다. 100건 배치는 0.20초(초당 500건), 25건 배치는 0.05초만큼 비례하여 정확히 대기합니다.
  - `BrokerBatchPoller`에 마이크로 배칭 루프를 도입했습니다. `BATCH_SIZE(100건)`에 도달하거나 첫 메시지 수신 후 `BATCH_LINGER_MS(100ms)`가 지날 때까지 메시지를 모아 전송하도록 개선했습니다.
- **결과**
  - 대량 트래픽 유입 시 100건 단위의 고효율 배치로 묶어 하위 Graylog를 초당 500건 상한으로 안정되게 보호하고, 유입이 줄어들면 지연 없이 큐를 비워내는 트래픽 평탄화를 달성했습니다.

## 3. Dead-Letter Queue(DLQ) 및 브로커 토픽 격리

- **문제**
  - 로컬 파일 기반 DLQ는 다중 컨테이너 환경에서 동시 쓰기 시 파일 락 경합이 발생했습니다.
  - 잘못 파싱된 비정형 데이터(포이즌 메시지)가 파티션 선두에 남으면 전체 배치가 지속해서 실패하여 정상 로그까지 밀리는 헤드오브라인 블로킹(HOLB)이 일어났습니다.
  - 전송 실패로 DLQ에 격리된 로그를 수동 개입 없이 자동으로 재처리할 메커니즘이 부족했습니다.
- **해결 방안**
  - DLQ 저장소를 브로커 전용 토픽(`security-logs.dlq`)으로 승격하는 `BrokerDeadLetterPublisher`를 구현했습니다. 원본 토픽, 파티션, 오프셋, 실패 사유 메타데이터 헤더를 함께 기록합니다.
  - `is_poison()` 판별 로직을 추가하여 손상된 메시지는 `security-logs.poison` 토픽으로 즉시 격리하고 오프셋을 커밋하여 파티션 진행을 정상화했습니다.
  - 유휴 폴링 주기나 정상 전송 직후 DLQ 토픽의 메시지를 읽어 메인 토픽으로 안전하게 되돌리는 자동 재전송 엔진을 구축했습니다.
- **결과**
  - 손상된 메시지로 인한 큐 정체를 해소하고, 다중 워커 환경에서도 충돌 없이 실패 로그를 격리하고 복구할 수 있는 안정성을 확보했습니다.

## 4. 결정적 이벤트 ID(_event_id) 기반 멱등성 확보

- **문제**
  - 최소 1회 전송(At-Least-Once) 파이프라인에서는 Graylog가 배치를 정상 저장했더라도 네트워크 타임아웃으로 응답을 받지 못하면 컨슈머가 동일 배치를 재전송합니다.
  - 수신 측에서 중복을 걸러내지 못하면 저장 로그 수가 전송 로그 수보다 많아져 정확한 무손실 검증이 불가능했습니다.
- **해결 방안**
  - GELF 페이로드에 브로커 파티션과 오프셋을 조합한 결정적 고유 식별자 `"_event_id": f"{partition}:{offset}"`를 주입했습니다.
  - 테스트 수신 서버(`mock_graylog_server.py`)에 수신 이벤트 ID 캐시를 두고, 중복 수신 시 HTTP 202는 반환하되 중복 카운트만 올리고 고유 저장 수에는 중복 합산되지 않도록 처리했습니다.
- **결과**
  - 재전송이 발생하더라도 멱등성을 보장하여 `전송 로그 수 == 고유 저장 로그 수` 대사 정합성을 확보했습니다.

## 5. 프로세스 간 슬라이딩 윈도우 EPS 및 최대 큐 적체량 텔레메트리 구축

- **문제**
  - Ingestor와 Consumer Worker가 별도 프로세스로 동작하여 순간 유입 속도, 방출 속도, 브로커에 완충된 최대 큐 적체량을 단일 모니터링 API에서 통합 확인하기 어려웠습니다.
- **해결 방안**
  - SQLite WAL 기반 메트릭 스토어(`SharedMetricsStore`)를 구현했습니다. 1초 단위 시간 버킷으로 인바운드와 아웃바운드 처리량을 기록하고 30초 이전 데이터를 자동 정리하도록 설계했습니다.
  - 최근 1~3초 슬라이딩 윈도우 평균 EPS와 최대 큐 적체량(`peak_queue_lag`)을 원자적으로 계산하여 반환하도록 구성했습니다.
- **결과**
  - 수천 건의 급증 트래픽 유입 시 인바운드 급증, 아웃바운드 500 EPS 제한, 큐 적체량이 0으로 해소되는 전체 흐름을 실시간 수치로 관측할 수 있게 되었습니다.

## 6. 단일 책임 원칙(SRP) 기반 모듈 분리와 Pydantic v2 설정 검증

- **문제**
  - 기존 컨슈머 워커 클래스 하나가 폴링, 속도 제한, GELF 변환, HTTP 전송, 커밋, DLQ 입출력까지 모두 처리하여 코드 응집도가 낮고 개별 테스트가 어려웠습니다.
  - 단순 `os.getenv` 파싱을 사용하여 음수 속도 제한이나 잘못된 설정값이 주입되어도 기동 시점에 잡지 못했습니다.
- **해결 방안**
  - 책임을 분리하여 개별 모듈(`BrokerBatchPoller`, `TokenBucketRateLimiter`, `GelfTransformer`, `GraylogDeliveryClient`, `ExplicitOffsetCommitter`)로 리팩토링했습니다.
  - Pydantic v2 기반 `PipelineSettings`를 도입하여 음수 입력 방지, 범위 검증을 서버 기동 즉시 수행하도록 강제했습니다.
- **결과**
  - 각 컴포넌트의 독립 단위 테스트가 가능해졌으며, 잘못된 설정 주입으로 인한 런타임 오류를 기동 단계에서 차단했습니다.

## 7. 메트릭 원장 분리와 무손실 회계 불변식 검증

- **문제**
  - 프로듀서 버퍼 고갈로 인한 영구 유실과 컨슈머 재시도 초과로 인한 DLQ 일시 격리가 단일 카운터(`dropped_logs`)로 관리되었습니다. DLQ 재전송 성공 시 카운터를 차감할 때 영구 유실 수치까지 잘못 깎여 정합성이 훼손될 위험이 있었습니다.
- **해결 방안**
  - 메트릭 원장을 두 카운터(`permanently_dropped_logs`, `dlq_quarantined_logs`)로 분리했습니다.
  - 카운터 차감 결과가 음수가 되면 트랜잭션을 즉시 롤백하고 `invariant_violations`를 증가시키는 원장 보호 로직을 적용했습니다.
  - 공식: `Total Sent == Total Received == Total Forwarded + permanently_dropped + dlq_quarantined == Graylog Stored`
- **결과**
  - 데이터의 영구 유실과 일시 격리를 명확히 구분하고, 원장의 수치 일치성을 엄격하게 입증했습니다.

## 8. 일시 정지(Pause) 기반 백오프 및 Cooperative-Sticky 리밸런스 제어

- **문제**
  - Graylog 장기 장애 시 백오프 루프 대기 시간이 길어지면 브로커가 컨슈머를 세션 타임아웃으로 간주해 강제 퇴출하고 무한 리밸런스를 일으킬 위험이 있었습니다.
  - 리밸런스 발생 시 HTTP 2xx 확인을 받지 못한 인플라이트 배치의 오프셋이 커밋되면 로그가 유실될 수 있었습니다.
- **해결 방안**
  - 백오프 진입 시 할당된 파티션을 `consumer.pause()`로 일시 정지하고, 정지 상태에서만 `poll(0)`을 호출해 디큐 없이 하트비트를 유지했습니다. 전송 성공 후 파티션을 재개(`resume`)합니다.
  - `cooperative-sticky` 리밸런스 전략을 적용하고 콜백을 등록했습니다.
    - `on_revoke`: 전송 확인이 안 된 배치는 커밋하지 않고 상태를 초기화하여 다른 컨슈머가 안전하게 이어받도록 처리.
    - `on_lost`: 소유권을 상실했으므로 어떤 오프셋도 커밋하지 않고 인플라이트 상태 폐기.
- **결과**
  - 다운타임이나 리밸런스 상황에서도 메시지 유실 없이 최소 1회 전송 복원력을 확보했습니다.

## 9. 우선순위 레인 분리 및 70:30 가중 드레인 구현

- **문제**
  - 대량 스캔 공격으로 수천 건의 로그가 브로커에 쌓여 있을 때, 단일 FIFO 큐에서는 침해 즉시 대응해야 하는 허니토큰 경보(`HONEYTOKEN_ACCESS`)가 일반 로그 뒤에 갇혀 전달이 수십 초 지연되는 문제가 있었습니다.
  - 반대로 우선순위 큐만 먼저 비우면 공격자가 허니토큰 이벤트를 계속 발생시킬 때 일반 로그가 굶주리는 기아(Starvation) 현상이 발생합니다.
- **해결 방안**
  - 허니토큰 및 심각도 2 이하 이벤트를 전용 토픽(`security-logs.priority`)으로 자동 분기 라우팅했습니다.
  - 컨슈머에 **70:30 가중 드레인 알고리즘**을 구현했습니다. 배치 슬롯의 70%는 우선순위 레인에 배정하고, 표준 레인 백로그가 있을 때 최소 30%를 보장하여 기아를 방지합니다. 한쪽 레인이 비면 다른 레인이 남은 슬롯을 흡수합니다.
  - 순서 보장 모델: 동일 IP 내에서는 CRC32 파티셔닝을 통해 시계열 순서를 보장하고, 두 레인 간 교차 순서는 실시간 대응을 위해 우선순위 레인이 먼저 처리되도록 설계했습니다.
- **결과**
  - 대량 백로그 적체 상황에서도 허니토큰 경보를 지연 예산(2.0초 미만) 내에 최우선 전송함을 실증했습니다.

## 10. 다중 인증, 식별자 기반 속도 제한 및 민감정보 마스킹

- **문제**
  - 비인가 트래픽 스파이크로 인한 인제스터 과부하 위험이 있었습니다. 클라이언트 IP 기준으로 속도 제한을 걸면 봇넷 환경에서 IP 테이블 메모리가 고갈될 위험이 있었습니다.
  - 로그 본문에 평문 API 키, 세션 토큰 등이 포함되어 SIEM에 그대로 저장되는 보안 위험이 있었습니다.
- **해결 방안**
  - `X-API-Key` 상수 시간 검증과 HMAC-SHA256 서명(`X-Timestamp`, `X-Signature`) 다중 인증을 적용했습니다. 인제스트 권한과 관리자 권한을 분리했습니다.
  - API 키 식별자 단위 인메모리 토큰 버킷 레이트 리미터를 구현하여 IP 카디널리티 폭증을 막고, 한도 초과 시 HTTP 429와 `Retry-After` 헤더를 반환하도록 했습니다.
  - 브로커 저장 직전 민감 키(`password`, `token`, `secret`, `api_key` 등)를 `"[REDACTED]"`로 마스킹하는 전처리 파이프라인을 구축했습니다.
- **결과**
  - 인제스트 진입점 보안과 입력 데이터 무결성을 강화했습니다.

## 11. 심층 헬스체크(Deep Healthcheck) 및 클라이언트 Fail-Open 서킷 브레이커

- **문제**
  - 단순 프로세스 생존만 확인하는 헬스체크는 디스크 풀이나 SQLite WAL 쓰기 락 경합 상태에서도 200 OK를 반환하여 로드밸런서가 결함 노드로 트래픽을 계속 보내는 문제가 있었습니다.
  - 미들웨어 장애 시 동기 HTTP 호출을 사용하는 비즈니스 API 서버나 IoT 제어 보드까지 스레드가 블로킹되어 서비스 전체가 멈추는 연쇄 장애 위험이 있었습니다.
- **해결 방안**
  - `/v1/health`에서 0.1초 타임아웃의 SQLite WAL 쓰기 락 프로브(`BEGIN IMMEDIATE; ROLLBACK;`)를 수행하도록 개선했습니다. 브로커 쓰기 불능 시 즉시 RFC 7807 규격의 `HTTP 503 Service Unavailable`을 반환합니다.
  - 클라이언트 라이브러리(`SafeSecurityLogClient`)에 비동기 유계 큐와 서킷 브레이커를 탑재했습니다. 비즈니스 호출은 0ms 만에 즉시 반환되며, 미들웨어 연속 실패 시 서킷을 열고 로컬 비상 파일(`client_fallback_logs.jsonl`)에 기록하는 Fail-Open 계약을 구현했습니다.
- **결과**
  - 관제 시스템 장애가 메인 비즈니스 서비스로 전파되지 않도록 연쇄 장애를 차단했습니다.

## 12. Prometheus 메트릭 및 Grafana 자동 프로비저닝 구축

## 13. 상용 Graylog 6.1 GELF HTTP 규격 분석 및 인덱싱 정합성 확보

- **문제**
  - 자체 Mock Graylog는 NDJSON 배치를 지원했으나, 실제 상용 Graylog 6.1의 GELF HTTP Input은 요청 바디당 단일 JSON 객체만을 디코딩하도록 구현되어 있었습니다. NDJSON 배치를 그대로 전송하면 첫 번째 로그만 처리되는 문제가 있었습니다.
  - REST API를 통해 인풋을 동적 생성할 때 노드 바인딩이 누락되면 컨테이너 재기동 시 인풋이 활성화되지 않는 문제가 있었습니다.
- **해결 방안**
  - Graylog 6.1 REST API를 통해 `Middleware GELF Ingest` 인풋(포트 12201)을 `global: true` 모드로 등록하여 클러스터 재기동 시에도 상시 자동 바인딩되도록 구성했습니다.
  - Graylog GELF 규격상 수신 시 언더스코어 필드(`_event_type`)가 인덱싱 시에는 언더스코어가 제거된 필드(`event_type`)로 검색된다는 점을 파악하고 쿼리 인터페이스를 정렬했습니다.
- **결과**
  - 상용 Graylog 6.1 및 OpenSearch 2.5 환경과의 엔드투엔드 프로토콜 정합성을 확보했습니다.

## 14. 2만 건 대규모 스파이크 및 5단계 무손실 감사 리포트 실증

- **내용**
  - 실제 호스트 Graylog 환경에서 대규모 20,004건(대량 스캔 20,000건 + 킬체인 3건 + 허니토큰 1건) 스파이크 부하 테스트를 구동하고 5단계 무손실 감사식을 검증했습니다.
- **실측 결과**
  - 순간 인입 속도: **4,448 logs/s** (4.5초 만에 2만 건 수락)
  - 최대 큐 적체량: **18,501건** (SQLite WAL 디스크 안전 버퍼링)
  - 평탄화 전송 속도: **초당 500건 상한(500 EPS) 준수**
  - 소진 소요 시간: **37.4초**
  - 무손실 정합성: `Sent (20,004) == Received (20,004) == Forwarded (20,004) == Stored (20,004)` (**0.0000% 로그 유실**)
- **결과**
  - 대규모 트래픽 스파이크 상황에서도 하위 SIEM 과부하 없이 100% 무손실 전송을 달성했습니다.

## 15. 웹 애플리케이션 진입점 및 SOAR IP 자동 차단 연동

- **내용**

  - 미끼 엔드포인트(`/api/honeytoken`)와 데모 초기화 엔드포인트(`/api/admin/unblock`)를 추가했습니다.

- **결과**

## 16. 미들웨어 유무(A/B) 실측 벤치마크 및 연쇄 장애 방지 입증

- **내용**
  - Graylog HTTP에 직접 전송할 때(Direct)와 미들웨어를 경유할 때(SOAR Middleware)를 비교하는 벤치마크 도구(`simulators/compare_middleware.py`)를 개발하고 600건 부하로 실측을 진행했습니다.
- **실측 결과**
  - **미들웨어 없을 때 (Direct to Graylog)**:
    - Netty I/O 스레드 경합으로 처리 속도가 **114 req/s**로 급락하고 클라이언트가 **5.25초 동안 블로킹**되었습니다.
    - 1,000건 동시 인입 시 Netty 스레드 포화(`ReadTimeoutException`)로 42초간 멈추며 **100% 전량 유실**되었습니다.
    - 웹 애플리케이션 전체가 마비되는 연쇄 장애(Cascading Failure)가 발생함을 확인했습니다.
  - **미들웨어 있을 때 (SOAR Middleware)**:
    - 비동기 WAL 인제스터를 통해 **1,656 logs/s(14.5배 빠름)**로 수집하여 **0.36초 만에 클라이언트 블로킹을 해제**했습니다.
    - 백그라운드에서 초당 500건으로 안전하게 평탄화하여 **0.00% 무손실**을 달성했습니다.
- **결과**
  - 미들웨어가 상위 서비스의 지연을 방지하고 하위 관제 시스템의 붕괴를 막는 필수 계층임을 실측 데이터로 증명했습니다.
