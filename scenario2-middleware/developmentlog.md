# 아키텍처 설계 및 문제 해결 기록

로그 스파이크 제어와 무손실 파이프라인을 구축하며 해결한 기술 과제와 설계 결정, 실측 결과를 정리한 문서입니다.

---

## 1. 백오프 대기 중 메시지 유실 방지와 오프셋 수동 커밋

- **문제**
  - 하위 SIEM(Graylog) 장애(HTTP 503 또는 타임아웃) 시 컨슈머가 지수 백오프 루프를 돌며 세션을 유지하기 위해 `consumer.poll(0)`을 호출했습니다.
  - 일반 `poll(0)`은 브로커에서 새 메시지를 디큐하여 반환합니다. 반환된 메시지를 처리하지 않고 버리면 장애 복구 후 오프셋을 커밋할 때 해당 메시지까지 함께 커밋되어 로그가 유실되는 문제가 있었습니다.
  - 인자 없는 `commit(asynchronous=False)`을 호출하면 컨슈머가 읽었던 모든 메시지의 오프셋이 일괄 커밋되는 결함도 있었습니다.
- **해결 방안**
  - 백오프 대기 루프에서 일반 `poll(0)` 호출을 제거했습니다.
  - 파티션을 일시 정지(`pause`)한 상태에서만 폴링하여 메시지 디큐 없이 세션 하트비트를 유지하도록 변경했습니다.
  - Graylog 전달이 확인된 배치 내 파티션별 최대 오프셋(`max_offset + 1`)만 지정하여 커밋하는 `ExplicitOffsetCommitter`를 구현했습니다.
- **결과**
  - 백오프 대기 중 디큐 횟수 0회와 파티션별 오프셋 정밀 커밋을 단위 테스트로 검증하고 메시지 유실을 차단했습니다.

## 2. 로그 개수 비례 토큰 버킷 스로틀링과 마이크로 배칭

- **문제**
  - 초기 레이트 리미터는 배치 내 로그 개수와 무관하게 배치당 토큰 1개를 차감했습니다. 그 결과 10건짜리 부분 배치와 100건짜리 배치가 동일한 대기 시간을 소모하여 큐 소진이 지연되었습니다.
  - 트래픽 유입 간격이 불규칙할 때 배치가 다 채워지지 않은 상태로 소규모 HTTP 요청이 빈번하게 나가는 비효율도 있었습니다.
- **해결 방안**
  - 전송할 실제 로그 개수(`acquire(len(messages))`)만큼 토큰을 차감하는 `TokenBucketRateLimiter`를 구현했습니다. 초당 500건 제한 기준 100건 배치는 0.20초, 25건 배치는 0.05초만큼 비례하여 대기합니다.
  - `BrokerBatchPoller`에 마이크로 배칭 루프를 적용했습니다. `BATCH_SIZE(100건)`에 도달하거나 첫 메시지 수신 후 `BATCH_LINGER_MS(100ms)`가 지날 때까지 메시지를 모아서 반환합니다.
- **결과**
  - 대량 유입 시 100건 단위 배치로 묶어 초당 500건 이하로 전송 속도를 유지하고, 유입량이 줄면 불필요한 대기 없이 큐를 비웁니다.

## 3. 데드레터 큐(DLQ) 브로커 토픽 격리 및 자동 재처리

- **문제**
  - 로컬 파일 기반 DLQ는 다중 컨테이너 환경에서 동시 쓰기 시 파일 락 경합이 발생했습니다.
  - 파싱할 수 없는 비정형 메시지(포이즌 메시지)가 파티션 선두에 남으면 전체 배치가 반복 실패하여 뒤따르는 정상 로그까지 밀리는 현상이 발생했습니다.
  - 전송 실패로 DLQ에 격리된 로그를 수동 작업 없이 재처리할 절차가 없었습니다.
- **해결 방안**
  - DLQ 저장소를 브로커 전용 토픽(`security-logs.dlq`)으로 분리하는 `BrokerDeadLetterPublisher`를 구현했습니다. 원본 토픽, 파티션, 오프셋, 실패 사유를 메시지 헤더에 함께 기록합니다.
  - `is_poison()` 판별 로직을 추가하여 손상된 메시지는 `security-logs.poison` 토픽으로 즉시 분리하고 오프셋을 커밋해 파티션 블로킹을 해소했습니다.
  - 유휴 주기마다 DLQ 토픽의 메시지를 읽어 메인 토픽으로 재발행하는 재처리 루프를 구현했습니다.
- **결과**
  - 비정형 메시지로 인한 큐 정체를 막고, 일시 장애로 격리된 로그를 유실 없이 복구합니다.

## 4. 파티션·오프셋 조합 이벤트 ID(`_event_id`) 기반 멱등성 보장

- **문제**
  - 최소 1회 전송 파이프라인에서는 Graylog가 배치를 저장했더라도 응답 타임아웃이 발생하면 컨슈머가 동일 배치를 재전송합니다.
  - 수신단에서 중복을 식별하지 못하면 저장된 로그 수가 전송한 로그 수보다 많아져 정합성이 깨집니다.
- **해결 방안**
  - GELF 페이로드에 브로커 파티션과 오프셋을 조합한 고유 식별자 `"_event_id": f"{partition}:{offset}"`를 주입했습니다.
  - 검증용 수신 서버(`mock_graylog_server.py`)에 이벤트 ID 셋을 두어 중복 수신 시 HTTP 202를 반환하되 중복 카운터만 증가시키고 저장 카운터에는 합산하지 않도록 처리했습니다.
- **결과**
  - 재전송이 발생해도 `전송 로그 수 == 고유 저장 로그 수` 정합성을 유지합니다.

## 5. 슬라이딩 윈도우 EPS 및 최대 큐 적체량 집계

- **문제**
  - Ingestor와 Consumer Worker가 별도 프로세스로 동작하여 순간 유입 속도, 방출 속도, 최대 큐 적체량을 하나의 API에서 조회하기 어려웠습니다.
- **해결 방안**
  - SQLite WAL 기반 공유 메트릭 스토어(`SharedMetricsStore`)를 구현했습니다. 1초 단위 버킷에 인바운드와 아웃바운드 처리 건수를 기록하고 30초 지난 버킷은 정리합니다.
  - 최근 1~3초 슬라이딩 윈도우 평균 EPS와 최대 큐 적체량(`peak_queue_lag`)을 트랜잭션 단위로 갱신하고 반환합니다.
- **결과**
  - 트래픽 급증 시 유입 속도 변화와 500 EPS 방출 제한, 큐 적체 해소 과정을 단일 메트릭 엔드포인트에서 실시간으로 확인할 수 있습니다.

## 6. 책임 분리 리팩토링과 Pydantic v2 설정 검증

- **문제**
  - 초기 컨슈머 워커는 단일 클래스에서 폴링, 속도 제한, GELF 변환, HTTP 전송, 오프셋 커밋, DLQ 처리를 모두 담당하여 결합도가 높고 단위 테스트 작성이 까다로웠습니다.
  - 환경변수를 단순 문자열로 파싱하여 음수 속도 제한이나 잘못된 설정값이 들어와도 실행 중에야 오류가 드러났습니다.
- **해결 방안**
  - 역할별로 모듈(`BrokerBatchPoller`, `TokenBucketRateLimiter`, `GelfTransformer`, `GraylogDeliveryClient`, `ExplicitOffsetCommitter`)을 분리했습니다.
  - Pydantic v2 기반 `PipelineSettings`를 도입해 프로세스 기동 시점에 타입과 값 범위를 검증하도록 구성했습니다.
- **결과**
  - 컴포넌트별 단위 테스트 작성이 쉬워졌고, 잘못된 환경변수 주입을 기동 단계에서 즉시 감지합니다.

## 7. 메트릭 원장 분리와 5단계 회계 불변식 검증

- **문제**
  - 프로듀서 버퍼 포화로 인한 영구 유실과 컨슈머 재시도 초과로 인한 DLQ 격리를 단일 카운터(`dropped_logs`)로 합산했습니다. 이 때문에 DLQ 재전송 성공 시 카운터를 차감하면 영구 유실 수치와 뒤섞여 원장 정합성이 깨질 수 있었습니다.
- **해결 방안**
  - 메트릭 원장을 `permanently_dropped_logs`와 `dlq_quarantined_logs` 두 카운터로 분리했습니다.
  - 차감 결과가 음수가 되면 트랜잭션을 롤백하고 `invariant_violations` 카운터를 올리는 방어 로직을 추가했습니다.
  - 검증 수식: `Total Sent == Total Received == Total Forwarded + permanently_dropped + dlq_quarantined == Graylog Stored`
- **결과**
  - 영구 유실과 일시 격리를 구분하여 파이프라인 전 구간 로그 수량을 대사할 수 있습니다.

## 8. 파티션 일시 정지 기반 백오프와 리밸런스 제어

- **문제**
  - Graylog 장애가 길어져 백오프 대기 시간이 늘어나면 브로커가 컨슈머를 세션 타임아웃으로 판단해 퇴출하고 리밸런스를 반복할 위험이 있었습니다.
  - 리밸런스 시점에 HTTP 2xx 응답을 받지 못한 배치의 오프셋이 커밋되면 로그가 유실될 수 있었습니다.
- **해결 방안**
  - 백오프 진입 시 할당된 파티션을 `consumer.pause()`로 정지하고, 정지 상태에서 `poll(0)`을 호출해 메시지 디큐 없이 세션만 유지합니다. 전송이 성공하면 `resume()`으로 복귀합니다.
  - `cooperative-sticky` 리밸런스 콜백을 구현했습니다.
    - `on_revoke`: 전송이 완료되지 않은 배치는 커밋하지 않고 버퍼를 비워 다음 컨슈머가 이어받도록 처리했습니다.
    - `on_lost`: 파티션 소유권을 잃은 상태이므로 오프셋 커밋 없이 인플라이트 상태를 폐기합니다.
- **결과**
  - 하위 시스템 장애나 컨슈머 리밸런스 중에도 오프셋 오커밋으로 인한 데이터 유실을 방지합니다.

## 9. 우선순위 레인 분리 및 70:30 가중 드레인

- **문제**
  - 대량 스캔 로그가 수천 건 적체된 상황에서 단일 FIFO 큐로만 처리하면 즉시 대응해야 하는 허니토큰 경보(`HONEYTOKEN_ACCESS`)가 일반 로그 뒤에 밀려 수십 초 지연되었습니다.
  - 반대로 우선순위 큐만 먼저 처리하면 고위험 이벤트가 연속 유입될 때 일반 로그가 처리되지 못하는 기아 현상이 생깁니다.
- **해결 방안**
  - 허니토큰 및 심각도 2 이하 이벤트를 우선순위 토픽(`security-logs.priority`)으로 분리 라우팅했습니다.
  - 컨슈머에 70:30 가중 드레인을 적용했습니다. 배치 슬롯의 70%를 우선순위 레인에 할당하고 표준 레인에 최소 30%를 보장합니다. 한쪽 레인이 비어 있으면 다른 레인이 잔여 슬롯을 사용합니다.
  - 동일 공격자 IP 내에서는 CRC32 파티셔닝으로 발생 순서를 보장하고, 레인 간에는 우선순위 레인을 먼저 처리합니다.
- **결과**
  - 백로그가 쌓인 상태에서도 허니토큰 경보를 목표 지연 시간(2.0초 미만) 안에 전달합니다.

## 10. 다중 인증, API 키 단위 속도 제한 및 민감정보 마스킹

- **문제**
  - 비인가 트래픽 유입 시 인제스터 보호 장치가 필요했습니다. 이때 클라이언트 IP 기준으로 속도 제한 버킷을 생성하면 스푸핑 공격 시 메모리 사용량이 급증하는 문제가 있었습니다.
  - 로그 본문에 포함된 평문 비밀번호나 API 키가 SIEM에 그대로 적재되는 보안 위험도 있었습니다.
- **해결 방안**
  - `X-API-Key` 상수 시간 비교와 HMAC-SHA256 서명(`X-Timestamp`, `X-Signature`) 검증을 적용하고 수집 키와 관리자 키 권한을 분리했습니다.
  - API 키 식별자 단위로 인메모리 토큰 버킷을 운용하여 메모리 급증을 막고, 한도 초과 시 HTTP 429와 `Retry-After` 헤더를 반환합니다.
  - 브로커 적재 전에 `password`, `token`, `secret`, `api_key` 등 민감 키 값을 `"[REDACTED]"`로 치환합니다.
- **결과**
  - 수집 엔드포인트 접근 통제와 민감 데이터 비식별화를 적용했습니다.

## 11. 스토리지 쓰기 헬스체크 및 클라이언트 Fail-Open 서킷 브레이커

- **문제**
  - 프로세스 생존 여부만 반환하는 헬스체크는 디스크 풀이나 SQLite WAL 쓰기 락 경합 상태에서도 HTTP 200을 반환하여 장애 감지가 늦어졌습니다.
  - 미들웨어 장애 시 비즈니스 API 서버가 동기 HTTP 요청을 보내면 워커 스레드가 대기 상태에 빠져 본 서비스까지 지연되는 문제가 있었습니다.
- **해결 방안**
  - `/v1/health` 호출 시 0.1초 타임아웃으로 SQLite WAL 쓰기 트랜잭션(`BEGIN IMMEDIATE; ROLLBACK;`)을 검사합니다. 실패 시 RFC 7807 포맷의 HTTP 503을 반환합니다.
  - 클라이언트(`SafeSecurityLogClient`)에 인메모리 유계 큐와 서킷 브레이커를 적용했습니다. 비즈니스 스레드는 큐 적재 후 즉시 반환되며, 전송 실패가 임계치를 넘으면 서킷을 열어 로컬 파일(`client_fallback_logs.jsonl`)에 기록합니다.
- **결과**
  - 스토리지 쓰기 장애를 즉시 식별하고, 관제 파이프라인 장애가 비즈니스 서버로 전파되는 것을 차단했습니다.

## 12. Prometheus 메트릭 노출 및 Grafana 자동 프로비저닝

- **문제**
  - 컨테이너 재기동 때마다 Grafana 웹 콘솔에서 데이터소스와 대시보드 JSON을 수동으로 등록해야 했습니다.
- **해결 방안**
  - `grafana_datasource.yml`과 `grafana_dashboard_provider.yml`을 구성하고 `docker-compose.yml` 볼륨에 마운트해 기동 시 자동 등록되도록 처리했습니다.
- **결과**
  - 컨테이너 실행 직후 별도 작업 없이 EPS, 파티션별 큐 적체량, 토큰 버킷 처리율을 대시보드에서 바로 확인할 수 있습니다.

## 13. Graylog 6.1 GELF HTTP 단건 전송 모드(`GELF_SPLIT_POST`) 및 커넥션 풀 튜닝

- **문제**
  - 자체 Mock 서버는 개행 구분(NDJSON) 배치 본문을 한 번에 처리하지만, 상용 Graylog 6.1의 GELF HTTP Input은 HTTP 요청당 단일 JSON 객체만 파싱합니다. NDJSON 배치를 그대로 보내면 첫 줄만 색인되고 나머지 로그가 누락되었습니다.
  - 배치 내 로그를 순차 단건 요청으로 보내면 네트워크 왕복 지연이 누적되어 처리 속도가 떨어졌습니다.
- **해결 방안**
  - `GraylogDeliveryClient`에 `GELF_SPLIT_POST` 옵션을 추가했습니다. 활성화 시 배치 내 로그를 `asyncio.Semaphore(25)` 제한 아래 비동기 병렬 단건 POST로 전송합니다.
  - `httpx.Limits(max_connections=50, max_keepalive_connections=25)`로 Keep-Alive 커넥션 풀을 설정하여 TCP 핸드셰이크 오버헤드를 줄이고, 배치 내 모든 요청이 2xx를 반환할 때만 성공으로 판정해 배치 원자성을 유지했습니다.
- **결과**
  - 상용 Graylog 6.1 환경에서도 누락 없이 초당 500건 처리 속도를 유지하며 적재합니다.

## 14. 프로듀서 `produce()` 핫패스 동기 SQLite 조회 제거 및 인메모리 캐싱

- **문제**
  - 2만 건 연속 부하 테스트 중 인제스터 응답 지연과 클라이언트 `ReadError`가 간헐적으로 발생했습니다.
  - 프로파일링 결과, FastAPI 이벤트 루프에서 호출되는 `LightweightProducer.produce()` 핫패스에 동기 SQLite 조회 두 곳이 있었습니다.
    1. 미소비 큐 적체량 한도(`max_unconsumed_lag`) 검사를 위한 `get_total_unconsumed_lag()` 조회
    2. 파티션 라우팅 시 토픽 파티션 수를 확인하기 위한 `_get_num_partitions()` 조회 (2만 건 인입 시 2만 회 `SELECT` 실행)
  - 백그라운드 쓰기 스레드가 배치를 디스크에 커밋하며 `BEGIN IMMEDIATE` 트랜잭션 락을 잡은 동안 이벤트 루프 스레드가 위 동기 쿼리를 실행하면 SQLite 락 대기(`busy_timeout=5.0s`)에 걸려 이벤트 루프 전체가 블로킹되었습니다.
- **해결 방안**
  - **비동기 주기 갱신 래그 캐시 도입**: `produce()`에서는 인메모리 딕셔너리(`get_cached_lag()`, 초기값 0)만 참조하도록 변경했습니다. DB 조회는 FastAPI `lifespan`에 등록한 백그라운드 태스크(`_broker_lag_refresh_loop`)가 `LAG_REFRESH_INTERVAL_SEC(기본 1.0초)` 주기로 `asyncio.to_thread(producer.refresh_unconsumed_lag, topic)`를 호출해 워커 스레드에서 수행합니다.
  - **토픽 파티션 수 인메모리 캐싱**: 런타임에 고정된 토픽별 파티션 수를 `_partition_count_cache`에 캐싱했습니다. 토픽당 최초 1회 캐시 미스 시에만 DB를 조회하고 이후 모든 `produce()` 호출은 메모리에서 즉시 반환합니다.
- **결과**
  - `produce()` 핫패스의 동기 SQLite 쿼리를 0회로 제거했습니다.
  - 20,000건 연속 2회(총 40,000건) 부하 테스트(`simulators/load_test_20k.py`)에서 `ReadError` 0건, 회차당 8.7~9.5초(2,100~2,280 logs/s)로 전량 수락을 확인했습니다.

## 15. A/B 벤치마크 연속 실행 시 로컬 프록시 `TIME_WAIT` 소켓 고갈 원인 격리

- **문제**
  - 14번 최적화로 미들웨어 단독 4만 건 연속 부하 테스트는 `ReadError` 0건으로 통과했으나, `compare_middleware.py`로 TEST A(Graylog 직접 전송 5,000~20,000건) 직후 TEST B(미들웨어 전송)를 연속 실행하면 TEST B 첫 요청에서 여전히 `httpx.ReadError`가 발생했습니다.
- **원인 격리 및 분석**
  - 서버 코드 결함인지 네트워크 계층 문제인지 분리하기 위해 인제스터 컨테이너 로그와 호스트 `netstat` 상태를 교차 확인했습니다.
  - 실패 시점에 인제스터 컨테이너 액세스 로그에는 요청 수신 기록이 0건이었고, 호스트 `netstat`에서 포트 `:8000`은 `LISTENING`만 존재해 요청이 컨테이너에 도달하기 전에 끊긴 것을 확인했습니다.
  - 반면 직전 TEST A가 호출한 `:12201` 포트에는 `max_keepalive_connections=0` 설정으로 인해 8,200개 이상의 `TIME_WAIT` 및 `FIN_WAIT_2` 소켓이 누적되어 있었습니다.
  - Windows Docker Desktop 환경에서 `localhost`는 IPv6(`[::1]`)로 우선 해석되어 `wslrelay.exe` 프록시를 경유합니다. TEST A가 수천 개의 단발 소켓을 생성하고 닫으면서 `wslrelay.exe` 소켓 테이블이 고갈되었고, 직후 `localhost:8000`으로 연결을 시도한 TEST B까지 프록시 계층에서 리셋된 것이 원인이었습니다.
- **해결 방안**
  - 시뮬레이터의 기본 접속 주소를 `localhost`에서 IPv4 루프백(`127.0.0.1`, `com.docker.backend.exe` 직접 경유)으로 변경했습니다.
  - TEST A의 `max_keepalive_connections`를 양수(50~150)로 높이는 방안도 실험했으나, 단일 프로세스가 이미 열린 TCP 연결을 재사용하면 Netty accept 큐 포화가 발생하지 않아 유실률이 0%로 나오는 왜곡이 확인되었습니다. 다수 클라이언트의 동시 연결 폭주를 모사한다는 TEST A의 시연 목적을 유지하기 위해 `max_keepalive_connections=0`은 그대로 두고, TEST A와 TEST B 사이에 3초 쿨다운을 두어 `TIME_WAIT` 소켓이 정리될 시간을 확보했습니다.
- **결과**
  - 5,000건 및 20,000건 A/B 연속 벤치마크에서 TEST A의 Netty 큐 포화 유실(20,000건 중 11,282건 유실, 56.4%)을 그대로 재현하면서 TEST B는 `ReadError` 없이 20,000건 전량 무손실(0.00%)로 완주했습니다.

## 17. 미들웨어 유무(A/B) 비교 및 2만 건 스파이크 실측 요약

- **A/B 비교 실측 (`simulators/compare_middleware.py --logs 20000 --concurrency 300`)**
  - **미들웨어 없이 Graylog 직접 전송 (20,000건)**:
    - Graylog Netty 큐 포화 및 타임아웃으로 20,000건 중 **11,282건 유실(56.4%)**, 34.55초 소요.
  - **미들웨어 경유 전송 (20,000건)**:
    - 인제스터가 18.36초 만에 20,000건을 모두 수락(**유실 0건**)하여 클라이언트 블로킹을 조기 해제하고, 백그라운드에서 초당 500건 이하로 평탄화하여 Graylog에 전량 전달.
- **2만 건 스파이크 5단계 감사 실측 (`simulators/spike_test_demo.py --spike-count 20000`)**
  - 순간 인입 속도: **4,448 logs/s** (4.5초 동안 20,004건 인입)
  - 최대 큐 적체량: **18,501건** (WAL 디스크 버퍼링)
  - 방출 속도 및 시간: 초당 500건 상한 준수, **37.4초** 만에 전량 소진
  - 수량 대사: `Sent (20,004) == Received (20,004) == Forwarded (20,004) == Stored (20,004)` (**유실 0건**)
