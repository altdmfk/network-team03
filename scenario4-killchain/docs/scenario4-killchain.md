### 시나리오 4. [고급 탐지 + 하드웨어] 킬체인(Attack Chain) 상관분석 & IoT 장비 제어 차단

단일 이벤트로는 차단 기준에 미달하지만, 시간순 연쇄 발생 시 침해 사고로 격상하여 물리 하드웨어(IoT 디바이스)까지 보호하는 시나리오. "우리는 성급하게 차단 안 하고, 공격 패턴 전체를 보고 확실할 때만 차단한다"

**동작 흐름 (단계별)**

| 단계 | 내용 | 발생 로그 |
| --- | --- | --- |
| 1. 정찰 (Recon) | 공격자가 Nmap으로 네트워크 내 API·IoT 디바이스 포트/경로 스캔. API 서버에 설치된 Wazuh 에이전트가 호스트 레벨에서 1차 탐지 | 동일 client_ip에서 1분 내 404 Not Found 5건 이상 -> Wazuh 알림 발생, Graylog로 전달 - 단독으로는 LOW 등급 경고 |
| 2. 침투 (Initial Access) | 정찰 직후 5분 이내 동일 IP에서 3번 시나리오의 유출 API 키 재사용으로 권한 획득 (브루트포스는 별도 구현하지 않고 3번 시나리오 로직 통일 사용) | Wazuh가 호스트 인증 로그 이상도 함께 탐지, 3번 시나리오의 api_key_compromised 이벤트 수신 - 단독으로는 MEDIUM 등급 |
| 3. 물리 장비 타격 (Action on Objectives) | 획득한 권한으로 IoT 디바이스 제어 API(POST /device/control)에 비정상 명령 전송 (강제 리부트, 센서 임계치 조작, 상태 변경 등) | IoT 제어 API 호출 로그 - 단독으로는 MEDIUM~HIGH 등급 |
| 4. 상관분석 판정 | Graylog가 Wazuh 알림 + API/IoT 로그를 모아 동일 client_ip 기준 10분 윈도우 내 1->2->3단계가 순서대로 모두 발생했는지 대조 | 3개 로그가 체인으로 묶이면 Kill-Chain 침해사고로 CRITICAL 격상 |
| 5. 자동 대응 | n8n이 체인 완성 신호 수신 즉시 다중 대응 트리거 | 아래 대응 항목 참고 |

**로그 수집 방법**

API 서버에 설치된 Wazuh 에이전트가 호스트 레벨(포트스캔, 비정상 인증 시도)을 1차 탐지해 알림 생성

메인 API 서버와 IoT 디바이스(ESP32-C3 SuperMini + MicroPython 경량 HTTP 서버, HTTP REST 통신 고정)가 동일 JSON 포맷으로 로그 전송: timestamp, client_ip, event_type, target_resource, status_code

Wazuh 알림 + 경량 버퍼링 미들웨어(시나리오2 인프라)를 거친 API/IoT 로그 -> Graylog로 통합 수집, 폭주 상황에서도 유실 없이 상관분석 가능하도록 동일 파이프라인 사용

**탐지 규칙 (구체적 조건)**

조건: 동일 client_ip 기준 1분 내 recon 이벤트(404) 5건 이상(Wazuh 1차 탐지) -> 5분 내 auth 이벤트(유출키 재사용) 발생 -> 10분 윈도우 내 device_control 이벤트 발생 순서 충족 시

3단계 중 2개 이하만 발생하면 개별 경고로만 유지(오탐 방지), 3개 모두 연쇄 완성 시에만 인시던트로 격상 - 단일 탐지가 아니라 연쇄 여부를 판단 기준으로 삼는 것이 핵심 차별점. 1~2단계만 발생한 경우 n8n이 `/warning`만 호출해 ESP32-C3 LED를 노랑(주의)으로 전환 - 완전 묵살하지 않고 상태는 보여주되 차단까지는 가지 않음

**자동 대응 프로세스 (n8n)**

| 대응 | 내용 |
| --- | --- |
| 네트워크 대응 | 공격자 IP 즉시 차단(pfSense 별칭) + 탈취된 세션/토큰 강제 회수 |
| 하드웨어 대응 (CRITICAL) | IoT 디바이스(ESP32-C3, HTTP REST)로 `/lockdown` 명령 전송 -> LED 깜빡임 3회 후 적색 고정 점등 + `/device/control` 전면 차단(423 반환) |
| 하드웨어 대응 (1~2단계만) | `/warning` 명령 전송 -> LED 노랑 전용 LED 점등으로 전환, 차단은 하지 않음 |
| 알림 | 메신저로 킬체인 전체 타임라인(1->2->3단계 각 발생 시각) 전송 |
| 기록 | 인시던트 티켓 자동 생성, 시나리오1 허니토큰 사고 기록과 연계 가능하면 교차 확인 |

**인시던트 관리 방안**

3단계 로그를 시간순으로 재구성한 타임라인을 인시던트 리포트에 자동 포함

Lockdown 해제(복구)는 조장(유지원) 수동 승인 절차로 분리 - 자동 잠금 해제는 하지 않음(오탐으로 인한 서비스 중단 방지)

**실측 검증 방법**

체인 완성 소요시간 측정: 정찰 시작부터 Lockdown 적용까지 전체 걸린 시간(목표: 10분 윈도우 내 자동 완결)

오탐 검증: 1~2단계만 발생시킨 경우 인시던트로 격상되지 않는지 확인(연쇄 판단 로직 검증)

물리 반응 검증: n8n 명령 전송부터 LED 점등까지의 지연시간 측정

데이터 정합성: 3단계 각 로그의 client_ip가 전부 일치하는지, 타임라인이 순서대로 재구성되는지 확인

**팀 결정 완료 항목**

- 2단계(침투): 유출키 재사용으로 통일 확정 (3번 시나리오 로직 그대로 사용, 브루트포스 별도 구현 안 함)
- 상관분석 윈도우: 10분으로 확정
- 정찰 단계 임계값: 1분 내 404 5건 이상
- Lockdown 해제 절차: 조장(유지원) 수동 승인으로 확정
- IoT 하드웨어: Pico W -> **ESP32-C3 SuperMini**로 최종 확정 (구매 완료)
- IoT 보드 ↔ n8n 통신 방식: HTTP REST로 고정
- LED 상태 체계: 파랑(부팅/Wi-Fi 연결 중) / 초록(정상) / 노랑(경고, 1~2단계만 탐지) / 빨강(Lockdown) 4색 전용 LED로 확정, 특이 케이스별 개별 블링크 패턴은 시연 직관성 저하 우려로 보류
- 네트워크 차단 방식: pfSense 별칭 (시나리오1과 통일)
- 호스트 레벨 1차 탐지에 Wazuh 에이전트 추가
